# vps1 load-test findings — 2026-09-24

The first full suite since 2026-09-02, and the first with continuous profiling: every bundle now
carries a Pyroscope CPU profile per service and `profiles/top.txt`.

Target `https://admin.highgeek.eu`; generator VPSM (51.195.116.123, ~20 ms RTT). Baseline VU counts
and 2-minute plateaus, so the numbers compare with [2026-09-02](2026-09-02-vps1.md). Fixture estate:
5 tenants, 1000 published items, 100 media assets, 5 Mode C + 5 Mode A sites.

## Headline

**Nothing failed:** every scenario ran at **0.00 % errors** with every threshold met. Getting a
real measurement, though, took two fixes and it found one incident:

1. **The harness could not sign in** after the edge BFF (ADR 0014); it now signs in through the
   edge the way the console does (`85a307e`).
2. **The edge's rate limit made a single-generator test impossible.** 97 % of delivery requests
   were 429s. Fixed by a new platform feature, rate-limit exemptions (`6446858`).
3. **The load made Tempo OOM-loop, 40+ times in a row.** Fixed and verified under load
   (`0a2cba0`, `a990487`).

Two real findings: the **admin plane is ~25 % slower** because RLS changed the plan of its list
queries (§4, the biggest), and **the WebP ladder encodes losslessly by accident** (§5).

## 1. The harness could not authenticate at all — **fixed** (`85a307e`)

Since BFF phase 5, the edge **strips** any client `Authorization` on the admin host's `/api`, and
`dcms-admin-spa` no longer holds `dcms.admin`. No token the harness could mint would ever reach
admin-api. `lib/mint-session.mjs` now signs in the way a browser does:

- `/.edge/signin`,
- identity's login form, including its antiforgery token, which is new since 2026-09-02,
- the `form_post` back to the edge,
- `/.edge/me` for the CSRF token.

Every admin request then carries the session cookie, `X-Dcms-Csrf` and a same-origin `Origin`.

Side effect: the edge refreshes tokens behind the session, so **the eight-minute cap on
authenticated runs is gone**.

## 2. One generator could not get past the edge's rate limit — **fixed** (`6446858`)

The edge now limits each client IP to 1200 req/min, in front of content-api's and site-host's
600/min. `delivery` at the baseline's 10 VUs came back **97.04 % 429**: 59,170 of 60,970, the
edge rejecting ~427 req/s. Its "25 ms p95" was mostly the edge refusing requests quickly.

Rather than lowering a DoS control for everyone, operators can now exempt addresses and ranges:
**Platform console → Operations → Rate limits**, behind `platform:ratelimits:manage`.
- **Where it's stored:** rows in `edge.rate_limit_exemptions`, audited.
- **How it's matched:** against the connection's real TCP peer at the edge.
- **Downstream:** the edge tells content-api and site-host via `X-Dcms-RateLimit-Exempt`, a
  header it strips from every inbound request.
- **Live:** it applies on a NATS broadcast, with a 5-minute re-read in case one is missed.
  Adding the exemption on vps1 took effect **in the same second**, with no restart.
- **Limits:** ranges wider than /8 (IPv4) or /32 (IPv6) are refused. The 30/min sign-in limit
  still applies to exempt addresses.

Verified both ways: exempt, `ratelimit` at 20 VUs saw **42,921 admitted, 0 refused**. After
removing the exemption, the same run saw **1,800 admitted and 93,307 refused (98.1 %)**. That's
exactly content-api's 600/min over three minutes, so the limit is back in force. **No exemption
is left in place on vps1.**

Also fixed on the way: `PermissionCoverageTests` never recognised `RequirePlatformPermission`, so
all fifteen delegated platform-api routes sat in its "legacy, ungated" list while each one does
name a `platform:*` key.

## 3. Load made Tempo OOM-loop — **Critical, fixed and verified** (`0a2cba0`, `a990487`)

From ~19:20 Tempo was **OOM-killed (exit 137) every 10–20 seconds**: 58 restarts. Two loops fed
it.

- **Ingest.** Alloy's Tempo exporter queues 1000 requests and retries for 5 minutes by default.
  Each fresh Tempo met that backlog replaying at full speed and died again, while Alloy sat at
  511.6 of 512 MiB holding the queue. Tempo had no ingestion limits below its defaults (15 MB/s,
  10,000 live traces), far more than 384m can buffer.
- **Compaction.** Once the backlog was gone, Tempo *still* died **within two seconds of every
  start**, with no load at all. The burst had left 40–50 MB blocks (401 blocks in total, most of
  them one flush per crash). Every start went straight into merging them, and was killed doing
  so.

The fix bounds both loops, not the memory:
- **Tempo ingestion:** 2 MB/s, 4 MB burst, 2000 live traces; beyond that it refuses with
  `RESOURCE_EXHAUSTED` rather than buffering.
- **Alloy's exporter:** a 100-request queue and a 1-minute retry cap.
- **Compactor:** `max_block_bytes` 30 MB and `v2_prefetch_traces_count` 100.

Result: **0 restarts** since 20:16, 62–119 MiB of 384, through the admin and media re-runs.

This will recur on the next host that takes a burst without these limits, so the memory limits
were deliberately left alone, the same lesson as the Alloy WAL spiral.

## 4. The admin plane is ~25 % slower: RLS changed its query plans — **High, not fixed**

The admin plane served **252 req/s against 334** at the same 15 VUs. The audit list's p95 went
86 → 148 ms. The profiles and traces split that into three parts.

**a) The list queries lost their "newest 50" index walk.** The audit list query did not change
since the baseline. What changed is who runs it: ADR 0015 moved admin-api from the table owner,
which bypasses RLS, onto `dcms_app`. `pg_stat_statements` shows its mean going from
**3.95 ms to 17.99 ms** for the same 51 rows per call. `EXPLAIN ANALYZE` on vps1 for tenant
`loadtest-02` (1,937 audit rows):

| run as | plan | time |
|---|---|---|
| owner (no RLS) | index walk on `OccurredAt`, stops at 50 | **2.0 ms** |
| `dcms_app` (RLS) | bitmap scan of **all 1,937** tenant rows, then top-N sort | **10.7 ms** |
| `dcms_app`, without the query's `OR` | the same full scan and sort | 10.3 ms |

So the cause is not the query's `OR` but RLS. The policy's `TenantId = current_setting(...)::uuid`,
added to the query's own `TenantId = …`, makes the planner estimate very few matching rows. On
that estimate, fetching them all and sorting looks cheapest. **The cost now grows with each
tenant's history**: every paged list over an RLS table (audit, content, media) reads the whole
tenant, not one page. At 100k audit rows, a page would cost hundreds of milliseconds.

Directions, in order of how contained they are:
- Keep the ordered walk explicit: a keyset `WHERE (OccurredAt, Seq) < @cursor` with `LIMIT`, or
  a `MATERIALIZED` CTE per partition.
- Help the estimate: a `LEAKPROOF` wrapper function for the tenant comparison, or extended
  statistics.
- For the platform-scope read path, run as the owner role on purpose.

Each needs checking against ADR 0015's guarantees, so this is **not** changed here.

**b) One extra database round-trip per query.** ADR 0015 phase 2 sends
`SELECT set_config('app.tenant_id', …), set_config('app.scope', …)` before **every** command.
That was **453,795 calls**, the most frequent statement on the server; a single audit request
made three of them, each waiting 1–5 ms under load. The fix is to send it once per connection
checkout, or in the same batch as the command it precedes.

**c) The BFF's own hop.** The edge now:
- decrypts the session cookie with Data Protection (`SP800_108 DeriveKeys` and the authenticated
  encryptor in its profile),
- loads the session from Redis,
- attaches the token.

That is about 3 % of the edge's CPU and a few milliseconds at p95. It's the cost of ADR 0014's
security gain. It is not the problem; (a) is.

## 5. The WebP ladder encodes losslessly, by accident — **High (cost), pre-existing**

`WebpLadderGenerator.cs:52` does `clone.Save(output, new WebpEncoder { Quality = 80 })` without
setting `FileFormat`, so ImageSharp encodes **lossless**. `Quality = 80` is meaningless there,
which says lossy was intended. The media-worker profile is conclusive:
- **~75 % of its busy CPU** (229 CPU-s in the window) is `SixLabors.ImageSharp.Formats.Webp.Lossless`:
  `CalculateBestCacheSize` 15.5 %, `HistoPriorityListPush` 11.5 %, `Vp8LHashChain.Fill` 10.9 %,
  `PredictorEncoder` 12.7 %.
- It has been this way since the initial commit (2026-06-15), so it is **not** today's
  regression. It was invisible until the profiles existed.

Fix: `FileFormat = WebpFileFormatType.Lossy`. For photographs that's typically several times
faster to encode and several times smaller on disk and on the wire. It changes the output
images, so it's a product decision, not changed here. The queue time (8.1 s here, 6.4 s on
2026-09-02) should drop with it.

## 6. Delivery and sites: fine, slightly faster

`delivery` is faster than the baseline at the same load: item p95 72 → 55 ms. The profiles say
where CPU goes:
- **edge:** TLS (`SslStreamPal.EncryptMessage`) and socket sends,
- **content-api:** socket I/O and EF Core per-context setup (`DbContext.get_DbContextDependencies`,
  `WarningsConfiguration.WithExplicit`, about 3 % together),
- **site-host:** almost pure proxying.

Nothing here is a hotspot.

`sitehost` asset p95 rose 121 → 147 ms. The 720 KB asset dominates it and bandwidth-bound numbers
over the internet move this much between runs. The page and index routes are within 5 ms of the
baseline.

## Harness changes in this round

- **Edge sign-in** (§1).
- **Profiles per run:** every bundle has `profiles/<service>.json` for the run window, and
  `profiles/top.txt`, which ranks functions by self CPU. It totals idle thread-pool waits
  separately, since `LowLevelLifoSemaphore.Wait` topped every service and said nothing. It also
  requests 16,384 nodes, because at the default a quarter of content-api's CPU was one `other`
  node.
- **`ratelimit.js` and the README** now describe exempting the generator instead of raising
  limits, and the check that the limit comes back afterwards.

## Caveats

- **`pg_stat_statements.txt` is cumulative since the last reset, not per run.** The mean and
  call counts in §4 come from comparing two entries that differ in query id, so they're sound;
  but the "top 40 by total time" list in any single bundle includes everything since the stats
  were last reset. The collector should diff a before/after snapshot. Not done yet.
- `sitehost`, `publish`, `mixed` and `sitebuild` ran partly while Tempo was looping (§3), which
  cost the host CPU. Their numbers are within noise of the baseline, so any effect was small,
  and it would make them look slower, not faster.
- Client-side numbers include ~20 ms RTT from VPSM. Server-side numbers come from Prometheus.
- The Pyroscope profiler was loaded in all ten services for the first time. The email-worker
  canary measured +13 MiB RSS and CPU within noise.
