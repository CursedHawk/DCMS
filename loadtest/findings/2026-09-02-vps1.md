# vps1 load-test findings — 2026-09-02

Four runs against vps1 (`admin.highgeek.eu`), git `586111b` (working tree dirty).
Bundles: `20260902T204351Z-sitehost-vps1`, `20260902T205447Z-admin-vps1`,
`20260902T211133Z-media-vps1`, `20260902T211656Z-sitebuild-vps1`.

Load originated from VPSM over the public internet: 20 ms RTT, so every client-side
number below carries that; server-side numbers come from Prometheus and do not.

## Headline

The platform is **not** close to breaking at these levels. 34,545 site requests at
216/s and 88,214 admin requests at 401/s, both with **0.00% errors** and every
threshold met. Nothing restarted; all pre-existing tenant sites stayed healthy.

What the runs did find is one large, fixable latency defect and one silently broken
piece of the observability stack.

---

## 1. 78% of every login is a synchronous Forgejo call — **Critical**

`identity /account/login` p95 is **975 ms** server-side, and it is reproducible:
five hand-timed logins ran 635–714 ms end to end.

The trace names the culprit exactly (`8b7f4e0e956a405d74c672de7fee8a46`):

```
    0.0   539.1ms  identity  POST /account/login
    1.8     1.8ms  identity  postgresql
  [~106ms gap: PBKDF2 password verify]
  107.9     0.9ms  identity  postgresql   x5, ~5ms total
  113.3   421.6ms  identity  PATCH http://forgejo:3000/api/v1/admin/users/test   <-- 78%
  535.9     1.2ms  identity  postgresql
```

**Cause.** `AccountEndpoints.cs:73` calls `forgejo.EnsureAsync(user, password, ct)` on
*every* sign-in — the "self-heal" backfill — which issues an unconditional
`PATCH /api/v1/admin/users/{name}` rewriting the user's Forgejo password even when
nothing has changed. All Postgres work in the request totals ~9 ms; the Forgejo hop is
47× that.

**Why it is worth fixing.** `ForgejoUserSync`'s own summary says the reliability model
is "perfect sync *without blocking the user*" — inline fast path, durable
`forgejo_sync_outbox` row on failure, drained by `ForgejoSyncWorker`. The outbox and
worker already exist. Login is simply on the wrong side of that design: it blocks on
the fast path for something that has no reason to be synchronous.

**Fix, cheapest first:**
1. Guard the call so it is not unconditional — sync only when `user.ForgejoUsername`
   is null or a `ForgejoSyncedAt`-style marker is stale. This alone removes it from
   virtually every login.
2. Or enqueue the outbox row directly on login instead of calling inline, and let
   `ForgejoSyncWorker` converge. Registration and password reset are rare and can stay
   inline; login is the hot path.

Either takes login from ~650 ms to ~120 ms, which is then dominated by PBKDF2 — the
cost you actually want to be paying.

## 2. `dcms:http_requests:rate1m` is permanently empty — **High**

Six Grafana panels across three dashboards read this recording rule, including the
headline traffic panels on `00-overview` and `02-http-traffic`. **All six have been
blank since they were written.**

**Cause.** Application metrics arrive over OTLP at the SDK's default **60-second**
export interval — measured, not assumed: `count_over_time(...[10m])` returns exactly
10 samples, i.e. one per 60 s. `rate()` needs two samples inside its window, so
`rate(x[1m])` over a 60 s-spaced series returns *nothing*. Verified directly:

| expression | result |
|---|---|
| `sum by (service) (rate(http_server_request_duration_seconds_count[1m]))` | **0 series** |
| same with `[2m]` | 6 series |
| `dcms:http_requests:rate1m` | **0 series** |
| `dcms:http_requests:rate5m` | 4 series |

Only the `rate1m` rule is affected; every `5m`/`1h` rule and `dcms:http_latency:p95`
are fine. This is also the failure mode that hides best: an empty graph on a
low-traffic platform looks exactly like a correct one.

**Fix.** Widen the rule's window in
`infra/observability/prometheus/rules/recording.yml` from `[1m]` to `[2m]` and keep the
record name so the six panels need no change. (Setting
`OTEL_METRIC_EXPORT_INTERVAL=15000` would also work and would give finer resolution
everywhere, at more storage — the rule change is the safe one.)

## 3. Site-host serves every request from MinIO — **confirmed, not yet costly**

Hypothesis 1 holds up as *described*, but at current load it is not hurting.

- site-host `/{**path}` p95 **41 ms** server-side (25.7 ms avg) for small static files.
- site-host 0.8 cores + MinIO 0.7 cores at 216 req/s — the two together were the
  largest CPU consumers on the box during the run.
- The extra round trip is measurable: page routes (one MinIO GET) p50 29.7 ms vs
  `/events/<uniq>` wildcard routes (two GETs) p50 33.8 ms — **~4 ms per extra GET**.
- Twelve repeated fetches of the same file showed no warm-up trend.

So the code reading (`SiteHostEndpoints.cs:19-49`: no cache, no ETag, whole object
copied into a `byte[]`) is confirmed by behaviour. It is a real inefficiency and the
obvious next optimisation, but it is **not** the platform's binding constraint today,
and this run does not justify prioritising it over finding #1.

## 4. Postgres's top load is its own monitoring — **Low, worth knowing**

`pg_stat_statements` ordered by total time is led not by application queries but by the
postgres-exporter's collection queries: 157 s total across 10,138 calls for the
`pg_stat_user_tables` query, plus 70 s for `pg_database_size`. Application statements
do not appear near the top.

Not a problem at this scale, but it means **`pg_stat_statements` must be reset
immediately before a run** for its output to be about the run. The collector does not
do this yet.

# Round 2 — media and sitebuild (added after the worker runs)

## 5. Every JetStream consumer processes one message at a time — **Critical**

`media` run: 4 concurrent uploaders, 3 minutes, 87 assets processed.

| measurement | value |
|---|---|
| queue-to-ready p50 / p95 | **6.4 s / 17.5 s** |
| worker processing time (p95, from `dcms_media_process_duration`) | 4.7 s |
| throughput | 0.48 assets/s |
| **media-worker CPU** | **1.0 core peak** (of 4) |
| host CPU / load | 0.5 / 2.8 |
| upload request p50 | 497 ms |

The box was idle. Three of four cores did nothing while the queue grew to a 17.5-second
p95 — at only four concurrent uploaders.

**Cause.** `MediaConsumerBase.cs:67` is

```csharp
await foreach (var msg in consumer.ConsumeAsync<MediaProcessRequested>(...))
{
    await HandleAsync(msg, stoppingToken);   // awaited inline -> strictly serial
}
```

`MaxAckPending` is a JetStream *prefetch* bound, not a concurrency setting. Awaiting the
handler inside the loop means exactly one message is processed at a time, so
`ImageProcessingConsumer.MaxAckPending => 4` has never produced any parallelism. The
measured 1.0 core against a 4.7 s job is precisely one job in flight.

The intent is unambiguous in the code itself — `VideoProcessingConsumer` carries
`MaxAckPending => 1; // transcoding is CPU-heavy`, which only makes sense if the number
were a concurrency limit.

**This is platform-wide.** All twelve JetStream consumers have the same shape:

```
EmailWorker/EmailSendConsumer.cs            ContentApi/Delivery/ContentCacheInvalidator.cs
ContentApi/Delivery/SearchIndexer.cs        SiteBuilder/SitePublishConsumer.cs
AdminApi/Audit/AuditIngestConsumer.cs       AdminApi/Audit/AuditLogProjector.cs
AdminApi/Chat/ChatFanoutConsumer.cs         AdminApi/Notifications/NotificationConsumerBase.cs
AdminApi/Tenancy/MembershipChangedConsumer.cs  AdminApi/Analytics/AnalyticsConsumer.cs
SiteHost/SiteCacheInvalidator.cs            MediaWorker/MediaConsumerBase.cs
```

**Fix.** Run handlers with bounded parallelism in `MediaConsumerBase` — a
`SemaphoreSlim(MaxAckPending)` around a tracked task per message, or
`Parallel.ForEachAsync` over the consume stream with
`MaxDegreeOfParallelism = MaxAckPending`. Then `MaxAckPending` means what its name, and
the video consumer's comment, already claim. Image processing is the case that benefits
most; keep video at 1 deliberately.

Expected effect: ~4× image throughput on the same hardware, taking the p95 queue from
17.5 s to roughly 4–5 s, with CPU going from 1 core to ~3.

## 6. site-builder and email-worker export no telemetry at all — **High**

172 site builds completed successfully during the `sitebuild` run. Prometheus recorded
**none of them**. `dcms_site_build_total` and `dcms_site_build_duration_seconds` do not
exist as series, and neither service appears in *any* series:

```
count by (service) (dotnet_process_cpu_time_seconds_total)
  -> admin-api, ai-gateway, content-api, identity, media-worker, site-host
     (site-builder and email-worker absent)

count({service="site-builder"})  -> NO SERIES AT ALL
count({service="email-worker"})  -> NO SERIES AT ALL
```

**Cause.** Both services deliberately opt out of the `*service-env` anchor in
`docker-compose.yml` — and for a good reason, documented in place: least privilege. The
builder runs a Postgres role scoped to the `sites` schema and a MinIO account scoped to
the site buckets, never the root credentials or a Vault token.

But `*service-env` also carries the only two telemetry variables:

```yaml
OTEL_EXPORTER_OTLP_ENDPOINT: "http://alloy:4317"
OTEL_EXPORTER_OTLP_PROTOCOL: "grpc"
```

and `AddDcmsServiceDefaults` "builds the tracer, meter and log pipelines unconditionally
but only attaches an exporter when this is set". So a **security decision silently
disabled observability for two services** — the anchor's own comment describes the
behaviour exactly, which is what made it invisible.

**Blast radius.**
- `infra/observability/grafana/dashboards/application/22-site-builds.json` — blank.
- `infra/observability/grafana/dashboards/application/23-email-ai-engagement.json` —
  the email half is blank. Nothing observes mail failing.
- `dcms:tenant_builds:rate1h` (recording.yml:71) can never produce data.
- No traces. `SitePublishConsumer` goes to real trouble to parent the build span to the
  originating click — "request → content_outbox → dispatcher → JetStream → here" — and
  that span tree never leaves the process.
- `scripts/obs-smoke.sh` cannot catch it: it lists all eight services in `SERVICES`, but
  its metric check runs `count($metric)` **globally**, so six services reporting is
  enough to pass.

**Fix.** Split the two OTEL variables into their own anchor and merge it into every
service, leaving the credential half of `*service-env` exactly as it is:

```yaml
x-otel-env: &otel-env
  OTEL_EXPORTER_OTLP_ENDPOINT: "http://alloy:4317"
  OTEL_EXPORTER_OTLP_PROTOCOL: "grpc"

x-service-env: &service-env
  <<: *otel-env
  ConnectionStrings__Postgres: ...
```

then add `<<: *otel-env` to `site-builder` and `email-worker`. Worth also making
`obs-smoke.sh` assert per-service, so this class of gap fails a smoke test rather than
waiting for someone to look at a blank dashboard.

## 7. Mode C builds are cheap — and the sandbox hypothesis is still untested

`sitebuild` run: 2 VUs, 3 minutes, **172 builds, 0 failures**.

| measurement | value |
|---|---|
| publish-to-live p50 / p95 | 2.09 s / **2.11 s** |
| site-builder CPU | **0.1 core** |
| host CPU / load | 0.2 / 2.0 |
| disk growth | ~1 GB for 172 builds (~6 MB retained per build) |

The p50-to-p95 spread is 19 ms. There was no queueing at all: two VUs against a serial
consumer at ~2 s per build is almost exactly its capacity.

**But this did not test what hypothesis 4 was about.** The fixture sites are Mode C
(`StaticFiles`), which extracts an already-staged bundle — it never launches the build
sandbox. `DCMS_BUILD_CPUS=2` / `DCMS_BUILD_MEM=2g` apply only to **Mode B** (`ReactApp`),
which runs `pnpm install` plus `vite build` in an ephemeral container. The claim that two
concurrent builds claim the whole box remains **unmeasured**, and needs a Mode B fixture
site to test. Note finding #5 makes it moot in one direction: the consumer is serial, so
two sandboxes cannot currently run at once regardless.

Retention is worth a look separately: 6 MB per build retained for rollback, at ~1 build/s
sustained, is a disk-growth path with no observed cap.

## 8. The media upload endpoint does image work inline — **Medium**

`admin-api /api/admin/media` p95 was **960 ms** server-side during the media run. The
handler buffers the whole upload into memory and then content-sniffs and re-encodes the
original through ImageSharp *inside the request*, before the asset is queued. That is
real CPU on the request path; the worker then re-reads and processes it again.

Lower priority than #5 — the queue is the user-visible delay — but it is why a 4 MB
upload takes half a second of server time before any queueing begins.

## Round 2 caveats

- Fixture PNGs were regenerated for this round. The original generator produced pure
  noise, which is incompressible: a 1920px frame was **7.3 MB**, so four VUs uploading it
  measured the load generator's uplink rather than the worker. They now use a gradient
  plus low-amplitude noise with PNG Sub filtering, landing at 4.3 MB for 1920px, which
  compresses roughly the way a photograph does.
- `media_queue_to_ready_ms` is measured from the upload **response**, not the request, so
  it is the worker's queue-plus-processing time and excludes upload bandwidth.
- **Postgres was not a factor.** Diffing `pg_stat_statements` across the media window:
  the heaviest application statement added 847 ms across 102,000 calls.
- **Per-consumer JetStream depth is not observable.** `nats_consumer_num_pending` and
  friends do not exist — the exporter publishes only account- and server-level consumer
  counts. The 17.5 s media backlog had to be inferred from the client side. Worth fixing
  if worker queues are going to be managed.

  > **Superseded 2026-09-03.** Half right and wrongly diagnosed. The exporter does publish
  > per-consumer depth; it publishes it as `jetstream_consumer_num_pending`, with
  > `stream_name` and `consumer_name` labels. prometheus-nats-exporter namespaces its
  > monitoring endpoints under `gnatsd_` and its JetStream collector under a bare
  > `jetstream_` — it emits nothing at all beginning `nats_`, so the queries here and the
  > twelve panels on the JetStream dashboard were all asking for a prefix that does not
  > exist on any deployment. Both are fixed; the depth was observable the whole time.
- Host stayed healthy throughout both runs: 0 restarts, load returned to 0.41, disk 72%,
  and all pre-existing tenant sites served normally.

# Round 3 — fixes shipped and verified

Commits `da842d9` (harness), `befea0a` (four fixes), `37cbf18` (scenario accounting),
deployed to vps1 by pipeline. Full suite re-run afterwards: **15 runs, ~400,000 requests**.

## What each fix did

### 1. Serial consumers — **fixed, 2.7× better**

`MediaConsumerBase` now runs `Parallel.ForEachAsync` over the consume stream with
`MaxDegreeOfParallelism = MaxConcurrency`. Identical run parameters, before → after:

| measurement | before | after | change |
|---|---|---|---|
| queue-to-ready p50 | 6,376 ms | **2,437 ms** | 0.38× |
| queue-to-ready p95 | 17,471 ms | **6,418 ms** | 0.37× |
| queue-to-ready max | 18,031 ms | 7,483 ms | 0.42× |
| assets processed in 3 min | 87 | **194** | 2.23× |
| media-worker CPU | 1.0 core | **2.5 cores** | 2.4× |
| host CPU | 0.5 | 0.9 | — |
| per-job duration p95 | 4.7 s | 9.4 s | 2.0× |

Two numbers deserve reading carefully.

**Per-job duration doubled, and that is the fix working.** Four jobs now share the CPU, so
each takes longer while the queue drains far faster. Throughput is the number that matters
and it went up 2.23×.

**It is 2.23×, not 4×, because the host is now the limit.** Host CPU went from 0.5 to 0.9.
The worker was using a quarter of the box and now uses most of it; there was never 4× of
headroom to collect. That also means image concurrency of 4 is now roughly the right ceiling
for this host — raising it further would take CPU from the request path rather than add
throughput.

Cost: the upload endpoint's p95 rose from 901 ms to 1,245 ms, because it now competes with
four busy workers for the same cores. See finding 8 — that endpoint does ImageSharp work
inline, which is why it is sensitive to CPU pressure at all.

`SitePublishConsumer` was made explicit but deliberately **not** raised, and the regression
check confirms it: 172 builds at p50 2,093 ms before, 171 builds at p50 2,093 ms after.
Byte-for-byte the same behaviour, now with `DCMS_BUILD_CONCURRENCY` available on a host with
the headroom.

### 2. Unobserved services — **fixed**

All eight services now export. `site-builder` went from **0 to 337 series**, `email-worker`
from **0 to 197**, and `dcms_site_build_total` / `dcms_site_build_duration_seconds_{bucket,count,sum}`
exist for the first time, so `22-site-builds.json` and `dcms:tenant_builds:rate1h` have data.

`obs-smoke.sh` now asserts per service and passes on all eight.

One honest caveat: `dcms_email_sent_total` still has no series. That is correct — it is a
counter, and no test in this suite sends mail. The service is exporting; the counter appears
the first time a message goes out.

This also explains why the fix looked like it had failed on first check: the metrics took
about two minutes to appear, because the OTLP export interval is 60 seconds. Finding 3's
root cause, demonstrating itself.

### 3. `rate1m` — **fixed**

`dcms:http_requests:rate1m` returns 4 series where it returned none. The six dashboard
panels reading it now have data, with no panel change.

### 4. Login — **fixed, 2.2× better**

Login went from a consistent **~650 ms** to **~300 ms** measured client-side over three
sequential requests (296 / 312 / 1275 ms, the last being the first request after the
container restart). The remaining time is PBKDF2 at ~104 ms plus TLS and 20 ms of RTT,

## New findings from this round

### 9. The publish pipeline is fast — hypothesis 6 refuted

**Publish-to-visible p50 is 69 ms, p95 122 ms**, end to end across admin-api → outbox →
OutboxDispatcher → NATS → ContentCacheInvalidator → delivery read. The concern that the
outbox poller's interval would floor publish throughput does not hold at this scale.

### 10. The rate limiter enforces exactly, and it hid a scenario failure

`ratelimit` admitted **1,800 requests over 3 minutes** — precisely 600/min — and refused
40,808. The control works exactly as configured.

It also produced the round's one genuine false alarm. The first `publish` run reported
18.48% errors and 6 items "never visible", which reads as a broken publish pipeline. It was
not: the scenario polls delivery every 250 ms, and 3 VUs doing that exceed 600/min, so the
polls were refused. With the limit raised for one window the same scenario ran **0.00%** with
zero never-visible. **A rate limiter on the read path makes any write-path scenario that
polls for visibility unmeasurable** — worth remembering before reading a publish failure as a
platform defect.

### 11. Disk pressure on vps1 is Docker, not data — **worth attention**

The host is at **75% of 72 GB** and `HostDiskFilling` alerts at 80%. Almost none of it is
platform data:

| what | size | reclaimable |
|---|---|---|
| Docker build cache | 22.34 GB | **21.52 GB** |
| Docker images (103, 31 active) | 40.12 GB | **26.44 GB** |
| MinIO (all tenant media + sites) | 3.7 GB | — |
| Prometheus | 702 MB | — |
| Loki | 115 MB | — |

Roughly **48 GB of 72 GB is reclaimable Docker artefacts**. `docker builder prune` alone
recovers 21.5 GB and is safe — vps1 pulls images by digest and does not build. The image
prune needs more care, because old images are what a `--rollback` deploy rolls back *to*, so
it should keep the last N releases rather than run bare `docker image prune -a`. Not run
here: deleting a rollback target is not a decision to make on someone's behalf.

### 12. Incidental support for the unpaged-list hypothesis

The second `admin` run was slower than the first: `GET /api/admin/content` p95 went
**53.5 ms → 79.5 ms** and overall throughput 401 → 334 req/s. Between the two runs the
`publish` scenario added ~1,200 content items to the same fixture tenants.

Consistent with `ContentEndpoints.cs:29` projecting every row for an instance with no
paging, but **not proven** — the audit table also grew across ~400,000 requests, and either
could explain it. A deliberate test with a tenant seeded to several thousand items would
settle it.

# Round 4 — the three render modes, and the panels that were never reading anything

2026-09-03, against vps1 (dev). Three subjects: Mode A and Mode B added to the build
scenario, an audit of every Grafana panel, and the last of the login cost.

## Site builds, by render mode

Two VUs, three minutes each, on a settled stack. `site_publish_to_live_ms` is queue wait
plus work; `dcms_site_build_duration_seconds` is the work alone.

| Mode | publish→live p95 | median | build work p95 | builds/s | errors |
|---|---|---|---|---|---|
| **C** StaticFiles — unzip a staged bundle | **367 ms** | 342 ms | sub-bucket | 5.75 | 0.00% |
| **A** StaticPrerender — assemble committed HTML/CSS in C# | **1.46 s** | 1.36 s | 0.95 s | 1.46 | 0.00% |
| **B** ReactApp — install + `vite build` in a sandbox | **36.95 s** | 34.41 s | 29 s | 0.057 | 0.00% |

The differences are the point, not the absolutes:

- **Mode A costs about a second more than Mode C** for a 12-page site. That second is a
  Forgejo read of the whole file map plus the assembler. It is not a problem — it is the
  number that says the assembler is not where to look.
- **Mode B costs about 33 seconds more than Mode A**, and all of it is the Node toolchain.
  A hundred times a Mode C publish.
- **Mode B's queue wait is visible directly.** A single build measured 16.5–18.3 s during
  seeding; at 2 VUs, publish→live is 34 s while the work is still 29 s. `DCMS_BUILD_CONCURRENCY`
  is 1, so the second build simply waits for the first.

## Finding: one Mode B build blocks every other site's publish

`--build-mode all`, 3 VUs, 4 minutes — the three pipelines contending:

| Mode | p95 alone | p95 in the mix | change |
|---|---|---|---|
| StaticFiles | 367 ms | **34.82 s** | **95×** |
| StaticPrerender | 1.46 s | 1.56 s | 1.07× |
| ReactApp | 36.95 s | 52.81 s | 1.43× |

A Mode C publish that costs 340 ms on its own waits **thirty-five seconds** behind a Mode B
build. Its `min` stayed at 338 ms — when it got a free consumer it was as fast as ever — so
this is head-of-line blocking, not saturation. `SitePublishConsumer` is one consumer on one
stream with `MaxConcurrency = 1`, and JetStream delivers in order, so a thirty-second build
holds every publish behind it regardless of what those publishes cost.

Raising `DCMS_BUILD_CONCURRENCY` is not the fix. A Mode B sandbox is allotted
`DCMS_BUILD_CPUS=2` of the host's four, so two concurrent Mode B builds are the whole box —
and nothing stops the two in flight both being Mode B. **The fix is to stop cheap builds
queueing behind expensive ones at all**: a separate subject or consumer for the git-backed
modes, so a Mode C publish is never behind a `pnpm install`.

> **Done** — see "Round 5" below. Publishes now carry one subject per render mode and
> site-builder drains them on separate consumers.

Not measured, and worth knowing before that decision: whether a Mode B build's 29 seconds is
mostly install or mostly `vite build`. `dcms_site_build_duration_seconds` covers both, and
the sandbox already writes a per-step log to object storage.

## Grafana: 77 of 224 panels were returning nothing

Audited by running every panel's expression against vps1's Prometheus and then, for each
empty one, checking whether its metric names exist at all. After the fixes, re-run against
the deployed stack: **13**, and all thirteen are correct — counters nothing has incremented

## Finding: Mode B was broken on vps1, silently

`dcms/site-build-sandbox:latest` was not on the host at all, so every ReactApp publish there
had been failing. Nothing detected it, and the deploy history was green.

It is the only image on the host that **no container ever references between builds** —
site-builder starts it with `docker run` per build. `docker image prune -a`, the obvious
thing to reach for when a disk alert fires, deletes exactly that one and leaves every
service image alone because a running container holds those. The host cannot re-pull it
either: registry credentials live only in the CI job.

`scripts/deploy.sh` pulled it and never checked afterwards that the tag resolved. It does
now, and fails the deploy rather than leaving a tenant to find out days later. The next
pipeline deploy restored it; both Mode B fixture sites then built first time.

## Login: the deferred write was still a write

Deferring the Forgejo sync had taken the `PATCH` off the request, but not out of existence —
`ForgejoSyncWorker` picked the row up 15 seconds later and rewrote an unchanged password, so
every sign-in still cost one admin write on the git server plus an outbox `INSERT` on the
request itself. Since every path that *changes* a credential already syncs inline, login's
job is repair, not maintenance.

Verified end to end on vps1 after the fix:

| | outbox rows written | login |
|---|---|---|
| Mirror synced 29 min ago | **0** | 187–283 ms |
| Mirror aged to 2 days, one login | **1** | 293 ms |
| …15 s later, worker drained, `ForgejoSyncedAt` re-stamped | 0 | — |
| Next login | **0** | 187 ms |

## Also found, not fixed

- **The build reaper's window was shorter than a build's own timeout.** 15 minutes, against
  `ReactAppBuilder`'s 10 for install plus 8 for the build — so a slow Mode B build could be
  marked Failed while still running, then overwritten by its own Succeeded. Now 25 minutes.
  *(Fixed, listed here because it was found rather than looked for.)*
- **Redis has no `maxmemory`.** `redis_memory_max_bytes` is 0, which is why that panel was
  blank. On a 7.6 GB host with no swap that is worth a deliberate decision; the panel now
  says so instead of showing nothing.
- **Audit fan-out logs a warning per publish under build load.** `NatsJSDuplicateMessageException:
  Duplicate of <seq>` at roughly one every two seconds during the Mode A run, each handled
  ("the record is already chained"). Harmless, but it is warning-level noise on a hot path.
