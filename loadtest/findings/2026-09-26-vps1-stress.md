# vps1 stress campaign: limits — 2026-09-26

The first campaign that looks for **where each surface stops**, not how it behaves at one load.
Every scenario ran as a staircase (`loadtest/stress.sh`): 2-minute plateaus at rising VU counts,
one evidence bundle per step. The generator was exempted from the rate limiters
(`loadtest/seed/exempt.mjs`) for the whole campaign and removed afterwards.

Target `https://admin.highgeek.eu` (vps1: 4 cores, 7.6 GB). Generator VPSM (51.195.116.123). Its
load average never went above 2.4 on 4 cores, so every number below is about vps1 and not about
the machine producing the load. Fixture estate as on 2026-09-24: 5 tenants, 1000 published items,
100 media assets, 5 Mode C + 5 Mode A sites.

## Headline: the limits of vps1

| surface | ceiling on vps1 | what sets it | past the ceiling |
|---|---|---|---|
| content delivery API | **~500 req/s** (was 380) | host CPU (edge TLS, the site-host hop, content-api, telemetry) | graceful now (**collapsed** before, §1) |
| hosted sites | **~540 req/s** with the artifact cache (was ~310); page p95 ≤ 184 ms at 400 VUs | transfer of the 1 MB assets: the edge's TLS work and ~380 Mbit/s (§4) | graceful: 0 errors up to 400 VUs |
| admin API | **~520 req/s** (was ~330) on 200-item tenants; **~217 req/s** on a 6,400-item tenant (was ~130, with OOM crashes) | host CPU; on big tenants, the audit list (RLS plans) | graceful now, 0 errors at 240 VUs (collapsed before, §1) |
| publish → visible | **~320 req/s** at 48 VUs, publish→visible p95 445 ms (was ~215 req/s, with 1 % errors at 48) | host CPU | graceful now (§1 was the 48-VU failure) |
| media pipeline | **~1.7 images/s** | host CPU; the lossy encoder now leads, the PNG re-encode is second (§5) | queue→ready grows linearly: 3.8 s at 4 VUs, 32.6 s at 32 |
| site builds, Mode C | **not reached**: 16 concurrent builds, publish→live p95 flat at 2.2 s | — | — |
| **mixed, realistic** | **~330 req/s** at 240 VUs, 0 errors, delivery p95 151 ms (was 225 req/s, delivery p95 3.8 s) | host CPU | graceful |

**The single most important finding:** under overload, delivery and admin throughput did not
level off, it *collapsed*: delivery dropped from 380 to 164 req/s with 9.5 % errors. The
cause was Postgres running out of connections, because no service capped its pool (§1).
That is fixed and verified: at 200 VUs delivery now serves **510 req/s with 0 errors**.

**Bottom line on capacity:** vps1 is CPU-bound. At every ceiling the host sits at 85–99 % CPU,
while no single container is throttled. Roughly a sixth of the box goes to recording the load
(Alloy + Tempo ≈ 0.5–0.65 cores; §6), and the TLS edge takes another 0.4–0.6.

## 1. Overload collapsed into Postgres connection exhaustion — **fixed** (`91471c3`, `37442a3`)

Past saturation, delivery and admin throughput *fell*. The logs say why:

```
Npgsql.PostgresException 53300: remaining connection slots are reserved for roles with the SUPERUSER attribute
```

- content-api: 1,212 of these in the 3-minute publish-48 window.
- admin-api: 474 in the 4-minute admin-120 window.
- In the delivery-200 window, Postgres held **95 of 100** connections, and the host's load
  average reached 49 on 4 cores.

No connection string set a pool size, so each service could open Npgsql's default of **100**,
against a single Postgres with `max_connections=100`. Under load, content-api and admin-api
grew their pools until Postgres refused them. The extra backends also cost Postgres CPU
(0.37 → 0.84 cores), and EF's retry-on-failure retried the refused opens. So each additional
user made the platform slower for everyone.

**Fix:** a `Maximum Pool Size` on every service's connection string (`docker-compose.yml`,
`docker-compose.prod.yml`). The budget is 90 connections of the 97 non-superuser slots:

| service | cap |
|---|---|
| admin-api | 35 |
| content-api | 25 |
| identity | 8 |
| site-host | 8 |
| media-worker | 5 |
| edge | 4 |
| ai-gateway | 3 |
| site-builder | 2 |

The comment beside content-api's connection string explains the budget.
- **Effect:** an overloaded service now waits up to 15 s for a free connection instead of
  failing, and Postgres runs about as many backends as it can serve.
- **Why admin-api got 35:** the first budget gave it 20, and it became pool-bound at
  ~145 req/s while Postgres sat at 0.7 cores. Its requests hold a connection longest (§3).
- **Not capped:** platform-api's connection string lives in Vault (`infra/vault/apply.sh`,
  which seeds it only when absent). It is console-only traffic and was left alone.

## 2. Tenant resolution queried Postgres on every request — **fixed** (`91471c3`, `03ac3db`)

`TenantStore` (`src/Shared/Dcms.Shared.Data/Tenancy/TenantStore.cs`) looked the tenant up by slug
on every request: ~680k calls in `pg_stat_statements`. Each call was one query plus a
connection checkout, an RLS `set_config` round trip and a `DISCARD ALL` on return.

Hits are now cached for 30 s.
- **Misses are not cached,** so a tenant created a moment ago resolves at once.
- **admin-api evicts on suspend, resume, create and delete,** so a change it makes applies to
  its next request. Other processes see it within 30 s, well inside the five minutes that
  site-host's route cache already allows a suspension.
- **Effect:** Postgres CPU in the delivery staircase fell from ~0.84 to ~0.3 cores, and peak
  delivery throughput rose from 380 to 510 req/s.
- **Tests:** three integration tests in `Tenancy/TenantResolutionCacheTests.cs`. Each one
  was checked to fail with its eviction removed.
- **Bug found by the campaign itself:** the first version evicted only on suspend and resume.
  The reseed (tear down, then re-create the same slugs) resolved `loadtest-01` to the purged
  tenant, so the new owner got 403s and the seeder's publish got 404s. `03ac3db` adds the
  create and delete evictions.

## 3. The admin plane's cost grew with the tenant — **fixed** (`6faec27`, `a3cb8f3`, `4bc9593`)

**Correction to the first version of this section:** the console's collection list was
*already* paged (`GET /api/admin/content/page`). The `admin` scenario called the picker route
`GET /api/admin/content` and labelled it "content", so the numbers below measured the picker
and not the list an operator waits on. The scenario now times both, separately.

What the follow-up found, on one 6,400-item tenant:

1. **The paged list still cost 537 ms per page** (`pg_stat_statements` mean). Postgres titled
   every item before taking 50, and no index matched the `(UpdatedAt, Id)` keyset.
   - Now the list finds the page's ids first, through a new index
     `ix_content_items_collection_recent`, then looks up those rows' versions by primary key.
   - `EXPLAIN ANALYZE` under `dcms_app`: **1.2 ms per page.**
   - A trap for anyone touching this query: comparing `"Id"` to `COALESCE(draft, published)`
     can never use an index under RLS. It stays a sequential scan per row, 200 ms, whether
     written as a join, a lateral, `LIMIT 1` or `OFFSET 0`.
2. **The unpaged picker route crashed admin-api.** Each call held every draft in memory.
   Under load admin-api died 3 times with `OutOfMemoryException`, and **46 % of admin
   requests got 502s, for every tenant.**
   - It is now paged: one shape, `{ items, nextCursor }`.
   - The picker and the builder preview follow the cursor to the end, so nothing is
     truncated. The assistant gets one page plus a cursor.

| 6,400-item tenant | before | after |
|---|---|---|
| 60 VUs | 131 req/s, content p95 1.6 s | **217 req/s**, content p95 **491 ms** |
| 240 VUs | 134 req/s, **46 % errors**, 3 admin-api crashes | **216 req/s, 0 % errors, 0 restarts** |

The slowest admin endpoint is now `GET /api/admin/audit`, at p95 1.3 s at 60 VUs. That is the
2026-09-24 RLS plan finding, still open.

The original analysis, kept for the record:

After the campaign's own writes, the fixture tenants held ~6,400 content items each, up from
200, plus ~15,000 audit events and ~250 media assets. Admin throughput then settled at
**~140 req/s whatever the pool size** (20 or 35): p95 1.2 s at 60 VUs, 3.3 s at 240.

A slow `GET /api/admin/content` trace from the admin-60 run breaks down like this:

| part of the request | time |
|---|---|
| total, in admin-api | 757 ms |
| `set_config` round trips (×2) | 21 + 15 ms |
| content query | **109 ms**, every row for the plugin instance |
| scheduled-publishes lookup | 32 ms |
| after the last query (serialization of an unbounded list) | ~500 ms |

- **Unpaged list:** open hypothesis #7 (`src/Services/Dcms.AdminApi/Cms/ContentEndpoints.cs`)
  is confirmed at scale. Its cost is linear in a tenant's items, and it holds a pooled
  connection while doing so. **Fix:** page it (`limit`/`cursor`), as audit and media already are.
- **RLS round trips:** one `set_config` precedes **every** command. That is a round trip that
  costs 15–21 ms under load, and 2 of this request's 4 queries were one. **Fix:** set the
  GUCs once per connection checkout, or prepend them to the command batch. This is the
  per-command overhead already noted on 2026-09-24.
- **Profile:** the highest self-time frame in admin-api is
  `AsyncLocalValueMap.MultiElementAsyncLocalValueMap.Set` (5.7 %). That means `AsyncLocal`
  churn per request (RLS scope, audit scope, Activity), worth one look.

## 4. Hosted sites: every page was 2–4 signed MinIO calls — **fixed** (`3d558de`)

At the sitehost ceiling (~310 req/s), CPU went to three places:
- **MinIO:** 1.09 cores, the largest consumer on the host.
- **site-host:** 0.81 cores, of which ~11 % was spent **signing S3 requests**
  (`V4Authenticator`, `HMACSHA256`, `GenerateSigningKey`).
- **edge:** 0.53 cores.

`SiteHostEndpoints.cs` runs `StatAsync` for each candidate filename, then a GET, for every page
view. There is no local cache (hypothesis #1, confirmed).

**Fixed:** `SiteArtifactCache` (`src/Services/Dcms.SiteHost/SiteArtifactCache.cs`), an
in-memory cache keyed by `ArtifactPrefix` + path.
- **What it holds:** which object each path resolves to, including "no such file", plus the
  bytes of files up to 256 KB.
- **Bounds:** a 64 MB cache of its own, and at most 8 fills at once.
- **Streamed as before:** larger files and Range requests.

Measured on re-seeded fixtures:

| VUs | before: req/s | before: page / asset p95 | cached: req/s | cached: page / asset p95 |
|---|---|---|---|---|
| 50 | 303 | 217 / 326 ms | **508** | **68** / 343 ms |
| 100 | 305 | 449 / 560 ms | **531** | **92** / 892 ms |
| 200 | 313 | 859 / 970 ms | **537** | **127** / 2.3 s |
| 400 | 306 | 1.7 / 1.8 s | **539** | **184** / 4.7 s |

At 100 VUs, CPU moved like this:

| container | before | cached |
|---|---|---|
| MinIO | 1.09 cores | 0.47 cores (nearly all of it the 1 MB assets) |
| site-host | 0.81 cores | 0.51 cores, while serving 74 % more |
| edge | 0.53 cores | 0.88 cores, now the busiest (TLS for 48 MB/s) |
| host overall | ~88 % | 75 % |

The limit is now moving the bytes of the scenario's ~1 MB image, not the lookups: the generator
received ~380 Mbit/s. The asset p95 grows with that queue.

The original design note, for reference: The artifact prefix is
unique per build, so its contents never change and the cache needs **no invalidation**, only a
size bound. Most of MinIO's 1.1 cores and all of the signing cost should go away, and the page
ceiling should rise well above 310 req/s.

## 5. Media — the WebP fix, measured

At 4 VUs, queue→ready p95 is **3.8 s, down from 8.1 s** on 2026-09-24 (`bbcbf6e`). The limit is
now ~1.7 images/s:
- media-worker averaged 1.7 cores, unthrottled, while the host ran at 82–92 % CPU.
- Its busiest frames are the lossy encoder (`QuantEnc.PickBestIntra4` 8 %,
  `QuantizeBlock` 5 %), which is the work it is supposed to do.
- **PNG re-compression** (`Deflater*`) takes ~20 %. `MediaSanitizer.SanitizeImage` re-encodes
  every upload with default PNG settings just to strip metadata. `PngCompressionLevel` 1–3
  would cut most of that for somewhat larger originals.
- `Array.Clear` / `SpanHelpers.ClearWithoutReferences` take ~11 %: freshly allocated image
  buffers being zeroed.

Media and delivery compete for the same 4 cores (hypothesis #4). A burst of uploads will slow
every other surface.

## 6. Telemetry under load

- **Cost:** Alloy + Tempo use **0.5–0.65 cores** at every ceiling. Sampling is deliberately
  off (`infra/observability/alloy/config.alloy`: every trace is kept for support). That is
  the right call at normal load, but it is the biggest fixed tax on capacity. Under overload,
  the errors + slow + 10 % policies already written in that file would return roughly half
  a core.
- **Span drops, by design:** past saturation Alloy rejects spans (`sending queue is full`).
  This is the bound added on 2026-09-24 working as intended: Tempo did not OOM-loop.
- **Alloy log spam:** Alloy logs each rejected batch. That was **34,236 error lines in four
  minutes**, which it then ships into Loki itself.
- **Alloy memory:** it lives at its limit, 511 of 512 MiB (393 MiB anonymous), with 0 OOM
  kills so far. Watch it; do not "fix" it by raising `mem_limit` (see the WAL death-spiral note).
- **Tempo:** restarted once during the campaign (14:15, exit 0, no log line, not OOM-flagged).
  It recovered by itself, and the cause is not provable after the fact.
- **Harness bug — fixed** (`37442a3`): Alloy's error lines filled the collector's
  2,000-line log query, so the admin bundle held none of admin-api's 6,418 connection errors.
  `collect.sh` now excludes Alloy from the lines and saves per-service error counts separately.

## 7. Smaller findings

- **Orphaned JetStream consumer — fixed** (`91471c3`). `SITES_EVENTS/site-host-cache` was a
  durable consumer bound on 2026-08-26 that nothing has pulled since. It showed a permanent
  147-message "backlog" in `pipeline_jetstream_pending`. The deploy retired its twin on
  `SITES` but not this one, and now retires both.
- **The outboxes are never pruned — open.**
  - `audit.audit_outbox` holds 190,905 rows, all applied.
  - `cms.content_outbox` holds 32,162 rows, all sent.
  - Only a tenant purge deletes from them. Their pollers are still fast (0.15 ms and 0.04 ms
    means over ~1.2M polls each), but both tables grow without bound. **Fix:** delete rows
    applied or sent more than N days ago, in `AuditMaintenanceWorker` and beside
    `OutboxDispatcher`.
- **Delivery has an extra hop.** Every public API request goes edge → site-host → content-api
  (`src/Services/Dcms.SiteHost/ApiProxy.cs`). That hop is part of why delivery is CPU-bound.
  It is by design, but it is not free.
- **The rate-limit exemption worked as designed** at up to ~500 req/s from one address.

## 8. Campaign hygiene

- **Rate-limit exemption:** `51.195.116.123/32` was added at 12:41 and removed at 16:32.
  After removal, `ratelimit` saw **1,200 admitted, 92,820 refused (98.7 %)**: the limit is back.
- **Fixtures:** torn down, 5/5 tenants removed.
- **Restarts:** no container restarted except Tempo (once, §6), and none were OOM-killed.
- **Disk:** vps1 went from 42 to 49 GB during the campaign (MinIO media, Prometheus, Loki),
  with 24 GB still free.
